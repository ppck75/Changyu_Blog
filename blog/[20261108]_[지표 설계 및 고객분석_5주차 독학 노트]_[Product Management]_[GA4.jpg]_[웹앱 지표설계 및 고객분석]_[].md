## 고객분석

지표가 무슨 일이 있어났는가?를 알려준다면, 고객 분석은 **누구에게 일어났고, 왜 그런가**를 알려준다. 

고객분석의 첫 원칙은 무엇일까?
    모든 지표는 최소 한 번은 쪼개서 볼 것

왜일까?  

전체 전환율 2%라는 숫자는 “100명 중 2명이 산다”를 뜻하지 않는다. 어떤 집단은 15%가 사고, 어떤 집단은 0.2%가 사는 상태의 가중 평균이다. 총량 지표는 이 차이를 평평하게 뭉개버린다.

이커머스에서 '챔피언'그룹은 고객은 5~10%에 불과하지만, 총 매출의 30~40%를 만들어내는 것을 생각해 보면, 모든 지표는 한 번 쪼개서 봐야하는 것을 생각해 볼 수 있다.

## 도메인 기반 지표설계

도메인별로 다루어야할 지표가 다르다. 

비즈니스·재무 (CFO, 경영진)
- 매출 / GMV  
- MRR · ARR  
- 공헌이익 · 마진  
- LTV / CAC  
- 회수기간  
- NRR · GRR  

프로덕트 (PM, 디자이너)
- DAU · WAU · MAU
- 활성화율 · TTV
- 리텐션 곡선
- 기능 채택률
- 퍼널 전환율
- 세션당 액션

마케팅·그로스 (마케터)
- 노출 · 도달 · CTR
- CPC · CPM · CPA
- ROAS
- 채널별 CAC
- 유기 유입 비중
- K-factor


## SQL, Python 지표설계 예시

| | Python  | **SQL** |
|---|---|---|
| 목적 | 탐색적 분석, 기준 결정 | **프로덕션 파이프라인 구축** |
| 산출물 | 차트와 의사결정 근거 | **재사용 가능한 VIEW 계층** |
| 강조점 | "왜 이 기준인가" | **"어떻게 매일 돌릴 것인가"** |
| 결과물의 수명 | 1회성 분석 | 지속 운영 |

### SQL 설계 원칙  
| 원칙 | 왜 |
|---|---|
| **CTE 를 계층으로 쌓는다** | 한 쿼리에 모든 로직을 넣으면 디버깅이 불가능하다 |
| **제외 규칙은 한 곳에만 쓴다** | 쿼리마다 복붙하면 반드시 갈라진다 |
| **VIEW 로 의미 계층을 만든다** | 분석자가 원본 테이블을 직접 건드리지 않게 한다 |
| **쿼리에 검증문을 붙인다** | 결과가 틀렸는지 쿼리 스스로 알려줘야 한다 |
| **날짜는 파라미터로** | 하드코딩하면 재실행 시 결과가 달라진다 |
